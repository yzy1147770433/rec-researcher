  ### 3. SourceRecord 当前如何变成 PassageRecord 和 EvidenceRecord

  转换代码在 src/rec_researcher/workflow/orchestrator.py:133。

  当前是一对一映射：

  SourceRecord
    id       ────────────────> PassageRecord.source_id
    snippet  ────────────────> PassageRecord.text
    score    ── clamp 0..1 ──> EvidenceRecord.relevance_score

  PassageRecord 的具体生成规则：

  - id = "passage-{全局序号}"
  - source_id = source.id
  - text = source.snippet
  - position = 序号 - 1
  - start_offset = 0
  - end_offset = len(source.snippet)

  随后 EvidenceBuilder：

  - 校验 passage.source_id 存在于 sources；
  - evidence_id = E1, E2, ...；
  - passage_id、source_id 原样保留；
  - excerpt 截断到 evidence_excerpt_length；
  - 默认 claim_hint = excerpt；
  - 使用已 clamp 的 Tavily SourceRecord.score。

  因此，当前 evidence 来自搜索摘要，不是网页全文，也不是混合检索结果。

  ### 4. retrieval/pipeline.py 的入口和返回值

  入口在 src/rec_researcher/retrieval/pipeline.py:67：

  async def retrieve(
      self,
      query: str,
      passages: Sequence[PassageRecord],
  ) -> RetrievalPipelineResult

  它不接收 SourceRecord，也不负责 fetch、chunk 或 dedup。调用者必须预先提供 passage corpus。

  返回值：

  RetrievalPipelineResult(
      passages: list[MMRResult],
      warnings: list[str],
  )

  执行阶段：

  PassageRecord corpus
    ├─ BM25Retriever.search()
    ├─ embed(all passage texts)
    ├─ vector_index.upsert_passages()
    ├─ embed(query)
    ├─ vector_index.search()
    ├─ weighted_reciprocal_rank_fusion()
    ├─ reranker.rerank(plain text documents)
    └─ maximal_marginal_relevance()
        └─ list[MMRResult]

  异常降级：

  - embedding 或 vector 任一失败：退化为 BM25；
  - reranker 失败：退化为 RRF；
    -空 corpus：安全返回空结果。

  ## E. 风险列表

  1. 持久 Milvus 污染和召回截断

     当前 Milvus collection 是持久共享的。搜索可能先返回旧运行 passage；pipeline 随后用本次 by_id 丢弃它们，导致本次有效候选被
     top-k 挤出。应采用 run-scoped collection、过滤条件或显式索引生命周期。

  2. 重复 embedding/upsert

     当前 pipeline 每次 retrieve() 都 embedding 全 corpus。按多个 task 调用会造成明显成本浪费和 budget 失真。

  3. reranker 空返回会清空有效候选

     provider 合法返回 [] 时不抛异常，pipeline 会令 ordered=[]，而不是退回 RRF。现有测试只覆盖 reranker 抛异常和空输入，没有覆
     盖“非空输入、空返回”。

  4. 返回类型边界不干净

     pipeline 返回 MMRResult，ResearchOutput.passages 和 EvidenceBuilder 需要 PassageRecord。虽然字段足以让部分运行时逻辑工作，
     但静态契约不兼容。

  5. 任务和证据失去关联

     sources 被全局合并后才统一生成 passages/evidence；TaskResult.evidence_ids 为空，报告无法知道哪条证据支持哪个 inquiry
     task。

  6. 只执行第一条搜索 query

     src/rec_researcher/workflow/orchestrator.py:216 忽略 search_queries[1:]，与 planner 可返回多个 query 的模型不一致。

  7. URL 去重逻辑未使用

     orchestrator 仅按 source.id 去重，没有使用已实现的规范化 URL 去重。

  8. 全文抓取的并发边界不足

     AsyncWebFetcher.fetch_many() 直接对全部 sources 执行 gather。接入时需在 orchestrator 或 fetcher 增加明确的 fetch
     semaphore。

  9. 配置校验不完整

     real 模式当前不要求 siliconflow_api_key、embedding_model 或 reranker_model。直接在 CLI 新建 provider 会把配置错误推迟到对
     象构造阶段。

  10. 分数语义不统一

     RRF、reranker 和 MMR 分数不是同一量纲；EvidenceRecord.relevance_score 又要求 0..1。需要定义用于 evidence 的规范化分数。

  11. 错误隔离粒度

     fetcher 能隔离常见单 URL 失败；但 batch embedding 任一异常会让整个 dense 分支退化。可以接受，但必须作为一次明确
     degradation 记录，而不能写成若干 source failure。

  12. 资源关闭

     LLM、Tavily、fetcher、SiliconFlow client 和 Milvus 都有生命周期。当前 CLI 没有统一的 async composition/context manager。

  13. 统计构造时机过早

     当前 statistics 在 passages/evidence 生成前构造。完整检索接入后必须移动到流水线完成之后。

  14. 测试语义需要更新

     现有 CLI 测试明确断言 real run 不创建 Milvus；接入后该断言必须替换为“只在完整 real composition 下创建并正确关闭/隔离”。
